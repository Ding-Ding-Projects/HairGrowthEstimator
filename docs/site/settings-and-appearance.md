# Settings and appearance

## Behavior

The website settings surface must provide English, playful Hong Kong-style Cantonese, and bilingual presentation; independent English and Cantonese funny-level controls; emoji decoration control; theme, density, accent, fonts, motion, and display-name settings; app-logo presets and local custom-image processing; scheduled settings; personal-vocabulary upload; accessibility modes; and per-element appearance editing.

Appearance editing must be non-destructive, reversible, local, and target-specific. Every rendered element must expose an Edit appearance command from its context menu and an accessible equivalent. Unsupported properties must remain visible with exact capability explanations.

## Configuration

Settings persist in browser-local state, with versioned schemas and reset actions. A custom logo must be decoded and converted locally under bounded byte, pixel, frame, time, and memory limits. Theme colors use a continuous picker and show multiple color-space representations, gamut warnings, alpha, and contrast.

The personal-vocabulary file contract is schema version 1 with exactly two root fields: `schemaVersion` and `entries`. `entries` is an object of source strings to replacement strings. The UTF-8 file is limited to 256 KiB, at most 4,096 entries, source strings from 1 through 160 characters, replacement strings from 0 through 1,000 characters, and a maximum JSON depth of 2. `handleVocabularyFile` rejects `file.size` above `MAX_VOCABULARY_BYTES` before calling `arrayBuffer()`, verifies that the resulting byte count still equals `file.size`, and then uses fatal UTF-8 decoding. Unknown fields, unknown schema versions, malformed UTF-8 or JSON, duplicate keys, unsafe object keys, non-string replacements, and values outside the declared bounds reject the complete file without partially applying it. `parseJsonStrict`, `validatePersonalVocabularyText`, and `validatePersonalVocabularyCache` implement the remaining contract in `site/security-contract.js`; the runtime uses them for cache application, reload validation, replacement, and clearing.

The external-file scanner in `tests/site/site.test.mjs` uses fatal UTF-8 decoding, requires the exact root fields `schemaVersion` and `entries`, requires a nonzero `PRIVATE_VOCABULARY_EXPECTED_COUNT`, checks the exact entry count without printing any replacement, verifies that every replacement is nonempty text, excludes only the public `Slop Machine` value, and asserts that the private replacement scan itself is nonempty. Its deliberate count fixture reported one failing test when the expected count was set to 0, then one passing test when the expected count was restored to 100. This proof covers the scanner contract only. It does not authorize bundling, logging, exporting, or displaying the private file or its entries.

Only a validated local cache may survive reload. The cache must be revalidated before each use. A missing, corrupt, stale, unsupported, or explicitly cleared cache restores the original shipped wording immediately. The source filename, source path, and file metadata are not cached. `applyVocabularyToOwnedText` applies validated replacements at the website-owned visible-text and accessible-name boundary while preserving exempt code, paths, technical content, user-authored display names and notes, local labels, authenticator codes, model names, and the factual release code name through `data-vocabulary-exempt`. `vocabularyStatusCopy` provides localized English, playful Cantonese, and bilingual copy for empty, `loading`, `loaded`, `replaced`, `invalid-preserved`, `invalid`, and `cleared` states without exposing mappings or source metadata. `#vocabulary-status` is a polite atomic status region. The choose action changes to Replace only when a valid cache exists, while Clear remains disabled without a valid cache. The command palette carries a separate `vocabulary-status` destination in addition to upload, replace, and clear. When School mode is active, all four destinations, personal-vocabulary controls, search results, replacement behavior, status copy, and references are absent from the rendered experience while the prior valid cache remains dormant for restoration after School mode is turned off. `SCHOOL_SENSITIVE_REGEX_OWNERS` identifies the language, playfulness, Cantonese voice, and personal-vocabulary owners whose active regex dialog must close. `applySchoolModeVisibility` also closes a context menu, appearance editor, or lock editor when its current target belongs to a School-sensitive or hidden surface.

State import accepts only the documented versioned browser export through a strict whole-file validator. `parseJsonStrict`, `validateBrowserState`, `validateAppearanceMap`, `sanitizeImportedState`, and `validateStoredStateEnvelopeText` implement the validation and sanitized-construction boundaries in `site/security-contract.js`. The runtime uses those functions for stored state, complete live-state snapshots, state import, appearance import, and appearance application. Appearance import accepts only allowlisted layer, state, and style fields with bounded counts and string lengths. Private locks, authentication entries, vocabulary cache, presentation-mode verifier, custom-logo bytes, and current presentation-mode state survive an ordinary state import only from the existing local state, never from the imported file.

## Failure modes

- Invalid or unsupported local files must not partially apply.
- Missing or corrupt cached settings must fall back to shipped defaults and report the fallback.
- A duplicate JSON key must be rejected before ordinary object parsing can overwrite the earlier value.
- An invalid personal-vocabulary cache must not keep replacements active or expose its contents in a recovery message.
- A state or appearance import containing unknown, unsafe, credential-bearing, or prototype-related fields is rejected or omitted by the documented sanitizer before any live state changes.
- A chosen font or voice that is unavailable must remain selected but show the active fallback.
- Clearing browser storage removes website preferences and locks.

## Security and privacy

Personal vocabulary and custom images remain local. Personal-vocabulary terms, mappings, payloads, cache content, filenames, paths, and file metadata are excluded from logs, exports, history snapshots, captures, analytics, prompts, clipboard operations, synchronized settings, and network requests. State and appearance imports must not accept credential material, executable markup, prototype keys, or arbitrary CSS property names. Website locks are convenience controls, not security boundaries.
